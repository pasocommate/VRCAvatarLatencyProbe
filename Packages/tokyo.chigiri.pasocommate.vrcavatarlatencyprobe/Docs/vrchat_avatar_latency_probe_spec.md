# VRChat アバター位置レプリケーション遅延 計測ギミック 仕様書 v5

## 1. 目的

VRChat ワールド内に常設できるギミックとして、**あるプレイヤーのアバター位置変化が、他プレイヤーのクライアント上で観測されるまでの遅延**を計測する。

### v3 からの変更点

v3 では1回の落下につき1つの閾値通過点で計測していたが、VRChat のアバター位置同期が ~100ms 間隔であるため、単一閾値では同期サイクルの同じ位相でしか計測できず、系統的な偏りが生じる可能性があった。

v4 では**マルチゲート方式**を導入し、1回の落下で5つのゲート（通過点）を120ms間隔で配置する。これにより100msの同期サイクル内の位相を均等にサンプリングでき、偏りのない計測が可能になる。

### 設計原則

- アクターを高所からの**自由落下**で運動させ、5つのゲート Y を通過した瞬間の時刻を計測
- ゲート間隔は120ms（VRChat の100ms同期間隔と非同期化するため）
- 3段階の集約: ゲート中央値 → 落下中央値 → 観測者間最小値
- アクター・オブザーバー間の時刻伝達には `[UdonSynced]` 変数を使用
- `Networking.GetServerTimeInMilliseconds()` の共有クロックでサーバー時刻基準の通過時刻を記録
- フレーム間線形補間で通過時刻を高精度化

---

## 2. 測定したい量

> プレイヤー A のアバターの「動き」がオブザーバー B のクライアントで観測されるまでの片道遅延

具体的には、同一のゲート Y を通過した瞬間のサーバー時刻の差:

```
latency = observer_crossing_time - actor_crossing_time
```

この遅延には以下が含まれる:
1. A のクライアント → VRChat サーバーへの位置データ送信
2. サーバーでの処理・転送
3. サーバー → B のクライアントへの位置データ配信
4. B のクライアントでのアバター位置補間・更新

---

## 3. 計測原理：マルチゲート落下方式

### 3.1 連続運動の利点

VRChat はアバター位置を ~10FPS でキャプチャ・送信するが、受信側では位置を**滑らかに補間**して表示する。テレポート（瞬間移動）は補間されない不連続変化であるため、検出タイミングは更新ティックの到着に縛られる。

一方、連続的な運動（例: 落下）では補間位置がゲートを通過する瞬間を正確に検出できる。通過がフレーム間のどの位置で起きたかを線形補間で算出すると、フレームレートによる量子化誤差も除去できる。

### 3.2 マルチゲートによる位相サンプリング

VRChat はアバター位置を ~100ms 間隔で同期する。単一のゲートで計測すると、そのゲートを通過するタイミングが同期サイクルの特定の位相に偏る可能性がある。

**マルチゲート方式**では、落下経路上に120ms間隔で5つのゲートを配置する:

- ゲート間隔: 120ms
- 同期間隔: 100ms
- gcd(120, 100) = 20
- 100ms / 20ms = 5 = ゲート数

これにより、5つのゲートは100msの同期サイクル内の位相を **0ms, 20ms, 40ms, 60ms, 80ms** と完全に均等サンプリングする。位相偏りのない計測が可能になる。

### 3.3 ゲート位置の物理計算

ゲートの Y 座標は自由落下の物理法則から算出する。ThresholdMarker などのシーンオブジェクトは不要。

```
gateY[i] = fallStart.y - 0.5 * g * (t₁ + i * Δt)²

ここで:
  g   = |Physics.gravity.y|  (≈ 9.81 m/s²)
  t₁  = FIRST_GATE_FALL_TIME = 0.6s  (落下開始から最初のゲートまでの時間)
  Δt  = GATE_INTERVAL_SEC    = 0.12s (ゲート間の時間間隔)
  i   = 0, 1, 2, 3, 4
```

FallStart Y=10m での具体的なゲート位置:

| ゲート | 落下時間 (s) | 落下距離 (m) | Y 座標 (m) | 通過速度 (m/s) |
|--------|-------------|-------------|-----------|---------------|
| G0     | 0.60        | 1.77        | 8.23      | 5.89          |
| G1     | 0.72        | 2.54        | 7.46      | 7.06          |
| G2     | 0.84        | 3.46        | 6.54      | 8.24          |
| G3     | 0.96        | 4.52        | 5.48      | 9.42          |
| G4     | 1.08        | 5.72        | 4.28      | 10.59         |

### 3.4 フレーム間線形補間

```csharp
// prevY >= gateY かつ currY < gateY のとき:
float frac = (prevY - gateY) / (prevY - currY);
int crossMs = prevServerMs + (int)(frac * deltaMs + 0.5f);
```

90fps の場合、1 フレームあたり約 0.07-0.12m の移動に対して補間精度は ~1ms 以下。

1フレームで複数ゲートを通過する場合（低FPS時）も、各ゲートについて同じフレーム境界点ペアから独立に線形補間することで正しい通過時刻が算出できる。

### 3.5 同期戦略

アクターは5つのゲート全通過後に通過時刻を同期変数で一括送信する:

- `[UdonSynced] int _syncedActorGateMs0..4`: 各ゲートのサーバー時刻
- `RequestSerialization()` で1回の送信に含まれるため、原子的に到着する

試行の進行状態は `[UdonSynced] int _syncedPhase` で全クライアントに通知される:
- `PHASE_SETTLING (1)`: テレポート直後、安定待ち
- `PHASE_FALLING (2)`: 落下中、観測開始
- `PHASE_CROSSED (3)`: 全ゲート通過済み、ゲート時刻が有効
- `PHASE_DONE (4)`: 全落下完了

## 4. タイミングパラメータ

| パラメータ | 値 | 理由 |
|---|---|---|
| `NUM_FALLS` | 5 | 5回の落下で中央値を算出 |
| `NUM_GATES` | 5 | 1落下あたり5ゲート。100ms同期サイクルの完全位相サンプリング |
| `FIRST_GATE_FALL_TIME` | 0.6s | 十分な速度（~5.9 m/s）で検出精度を確保 |
| `GATE_INTERVAL_SEC` | 0.12s | 120ms間隔。gcd(120,100)=20 → 位相20ms刻み |
| `SETTLE_TIME` | 0.5s | テレポート後のキャラクターコントローラー安定待ち |
| `INTER_FALL_DELAY` | 1.5s | 落下間の待ち（着地 + 同期伝搬のマージン） |
| `FALL_TIMEOUT` | 3.0s | ゲート到達不能時の打ち切り（FALLING 開始から） |
| `COOLDOWN_SEC` | 5.0s | 再測定までのクールダウン |
| 落下開始 Y | 10m | 5ゲート（最終 Y≈4.28m）を収容する十分な高さ |

## 6. 落下フロー

### 6.1 アクター側（1 落下あたり）

```
1. FallStart (Y=10) にテレポート
2. phase = SETTLING を同期、0.5 秒待つ
3. phase = FALLING を同期、ゲート監視開始 (_nextGateIndex = 0)
4. 毎フレーム: LocalPlayer.GetPosition().y を取得
5. 各ゲートについて prevY >= gateY && currY < gateY で通過検出
6. 線形補間で各ゲートの通過サーバー時刻を算出
7. 5ゲート全通過後: _syncedActorGateMs0..4 に記録、phase = CROSSED を同期
8. 1.5 秒待って次の落下へ
```

### 6.2 オブザーバー側（1 落下あたり）

```
1. phase = SETTLING 受信 → per-fall 状態リセット
2. phase = FALLING 受信 → ゲート監視開始 (_obsNextGateIndex = 0)
3. 毎フレーム: actor.GetPosition().y を取得
4. 各ゲートについて obsPrevY >= gateY && currY < gateY で通過検出
5. 線形補間で各ゲートの通過サーバー時刻を算出
6. 5ゲート全通過後、phase = CROSSED 受信を待つ
7. latency[i] = obsGateMs[i] - actorGateMs[i] (i=0..4)
8. 5レイテンシの中央値 → この落下の結果
```

## 7. 結果集約階層

3段階の集約で最終結果を算出する:

### 7.1 ゲート中央値（1落下内）

1. 5ゲートのレイテンシ（0ms以上、5000ms未満のもの）を収集
2. 挿入ソートで昇順化
3. 中央値（P50）を線形補間で算出
4. → この落下の結果

### 7.2 落下中央値（1観測者内）

1. 5回の落下結果を収集（-1 = 無効を除外）
2. 挿入ソートで昇順化
3. 中央値（P50）を線形補間で算出
4. → この観測者の結果

### 7.3 観測者間最小値（最終結果）

1. 全観測者の結果を収集
2. 最小値を選択
3. → 最終結果として全クライアントに配信

### 7.4 レポートプロトコル

各オブザーバーは自身の落下中央値をアクターに報告する:
- 報告はスロット番号順に 2 秒間隔でスタガーされる（同期変数の所有権競合を回避）
- `_syncedReportSlot`: 報告元スロット番号（-1 = 最終結果）
- `_syncedMedianMs`: 中央値
- `_syncedSampleCnt`: 有効落下数
- アクターは全報告を受信後（またはタイムアウト後）最小値を算出

## 10. 計測精度

| 要因 | 影響 |
|---|---|
| フレームレート (アクター) | 90fps → ~11ms フレーム間隔。線形補間で ~1ms 以下 |
| フレームレート (オブザーバー) | 同上。VRChat の補間位置を観測するため連続 |
| サーバー時刻同期 | 数ms のオフセット（Photon 基盤）— 系統誤差として中央値に含まれる |
| アバター補間 | VRChat は ~10FPS の受信位置を滑らかに補間。連続変化として観測可能 |
| 落下物理の再現性 | キャラクターコントローラーの重力は一貫。試行間の差は無視できる |
| 位相サンプリング | 5ゲート×120ms間隔で100ms同期サイクルの位相を均等カバー |

**v3 との比較:**
- v3: 単一閾値で同期位相の偏りが生じうる
- v4: 5ゲートの位相サンプリングで偏りを解消

**典型的な計測値:**
- 同一リージョン・良好な接続: 80-200ms
- クロスリージョン: 200-500ms
- 不良接続: 500ms+

## 11. エッジケース

| ケース | 対応 |
|---|---|
| アクターが途中退出 | OnPlayerLeft で即終了、収集済みデータで結果算出 |
| 他プレイヤーが計測中にボタンを押す | 拒否 HUD を表示 |
| 落下がゲートに到達しない | FALL_TIMEOUT (3s) でスキップ、次の落下へ |
| 1フレームで複数ゲート通過 | while ループで全ゲートを処理。各ゲートは同じフレーム境界点から独立に補間 |
| ゲートが部分的にしか検出されない | 有効なゲートのレイテンシのみで中央値算出 |
| 同期遅延で CROSSED 受信が遅れる | オブザーバーはローカルにゲート時刻を保存し、OnDeserialization 到着時にマッチング |
| サーバー時刻の int オーバーフロー | 後述「VRChat API の注意点」を参照。`!= 0` で判定し、`> 0` は使用しない |

## 12. VRChat API の注意点（開発知見）

本ギミックの開発中に判明した、VRChat (Udon) 固有の注意点をまとめる。

### 12.1 `Networking.GetServerTimeInMilliseconds()` は負値を返す

**現象**: `Networking.GetServerTimeInMilliseconds()` の戻り値が負の整数になる。

**原因**: 戻り値の型は `int`（32ビット符号付き整数）。VRChat のサーバー時刻はインスタンス単位ではなく **Photon サーバー単位** で管理されるため、サーバーの稼働時間が 2³¹ ms ≈ 24.8 日を超えると int オーバーフローにより負値になる。VRChat インスタンスの寿命は数時間〜数日程度だが、サーバープロセス自体はそれより長寿命である。

**対策**:
- タイムスタンプの有効/無効判定に `> 0` を**使ってはならない**。`!= 0`（0 を未記録マーカーとして利用）で判定する。
- **2つのタイムスタンプの差（`t2 - t1`）は正しい値になる**。int のオーバーフローは環状（modular arithmetic）であり、差分が int の範囲内（約±24.8 日）に収まる限り正確。レイテンシ計測（数百ms〜数秒）では問題にならない。

```
例: 実測値
  Actor gate crossMs   = -1417825358
  Observer gate crossMs = -1417824822
  latency = -1417824822 - (-1417825358) = 536ms  ← 正しい
```

### 12.2 `OnDeserialization` と同期バッチの競合

**現象**: アクターが `PHASE_SETTLING` → `PHASE_FALLING` と短時間に2回 `RequestSerialization()` を呼ぶと、VRChat の同期バッチングにより `PHASE_SETTLING` がオブザーバーに届かず、**直接 `PHASE_FALLING` を受信する**ことがある。

**対策**: オブザーバーの自動開始条件を `_syncedPhase == PHASE_SETTLING` のみでなく `(_syncedPhase == PHASE_SETTLING || _syncedPhase == PHASE_FALLING)` にする。同期バッチで中間状態がスキップされることを前提に設計する。

**一般原則**: `RequestSerialization()` で送信される変数の値は「最後に書き込まれた値」が送信される。短時間に複数回呼んでも、実際のネットワーク送信は VRChat のフレームタイミングで1回にまとめられるため、中間値は消失しうる。

### 12.3 リモートアバター位置の不連続ジャンプ

**現象**: テレポート直後やネットワーク遅延回復時に、`VRCPlayerApi.GetPosition()` で取得するリモートアバターの位置が大きく不連続にジャンプし、前フレームの位置（`prevY`）が既にゲートより下にある状態が生じることがある。通常の通過検出（`prevY >= gateY && currY < gateY`）だけではこのケースを捉えられず、検出ループが停止する。

**対策**: `else if (currY < gateY)` の分岐を追加し、既にゲートを通過済みの場合はスキップ扱いで次のゲートへ進む。アクター側は `currServerMs` をフォールバック値として記録し、オブザーバー側は `0`（無効マーカー）を記録してレイテンシ計算から除外する。

### 12.4 UdonSharp の型制約

UdonSharp では以下の機能が使用できない。設計時に注意が必要:

| 制約 | 回避策 |
|---|---|
| `[UdonSynced]` に配列を指定できない | 個別変数 `_syncedActorGateMs0..4` で代替 |
| 多次元配列が使えない | 1次元配列にインデックス計算（`fall * NUM_GATES + gate`）で格納 |
| ジェネリクスが使えない | 型ごとに個別のメソッド/配列を用意 |
| `List<T>` 等のコレクションが使えない | 固定長配列 + カウンタで管理 |

## 13. 制約事項

- **アクター自身の遅延は測れない:** 自分の位置変化は即座に反映されるため、他プレイヤーに観測してもらう必要がある
- **計測対象は位置レプリケーション:** アニメーション・表情等の遅延とは異なるパイプラインの可能性がある
- **物理的な高さが必要:** 落下のために 12m の垂直空間が必要。ワールドの天井や衝突ジオメトリに注意
